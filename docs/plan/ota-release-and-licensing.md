## 3. قرار OTA المقترح وأسبابه

**التوصية: electron-builder للتغليف + electron-updater للتحديث + GitHub Releases العام لتوزيع الملفات.** لا يلزم خادم حسابات أو وضع GitHub token داخل التطبيق لتحقيق التنزيل العام. GitHub يتيح ملفات الإصدار بحسب صلاحية قراءة المستودع؛ يُختبر الوصول المجهول فعلياً بعد إتاحته للعامة. [وثائق GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases).

| البديل | الميزة | القيد | التقييم للمشروع |
| --- | --- | --- | --- |
| إبقاء Forge واستخدام Electron autoUpdater | أقل تغيير في التغليف الحالي | المحدث المدمج لا يدعم Linux؛ نحتاج مساراً إضافياً له | ممكن، لكنه يزيد اختلاف المنطق والصيانة بين الأنظمة |
| electron-builder + electron-updater | أدوات تغليف وتحديث مرتبطة، وملفات تعريف تحديث مولدة، ودعم أهداف على الأنظمة الثلاثة | انتقال Squirrel إلى NSIS، والتحقق من توقيع Linux يحتاج معالجة مستقلة | الخيار الموصى به، بشرط اجتياز تجربة انتقال واختبارات مثبّتات حقيقية |

المحدث المدمج في Electron يدعم Windows وmacOS ويشير إلى مديري الحزم على Linux. أما electron-updater فيدعم NSIS على Windows ولا يدعم Squirrel.Windows. macOS يحتاج ZIP لتحديث التطبيق حتى لو كان التنزيل الأول DMG. [Electron autoUpdater](https://www.electronjs.org/docs/latest/api/auto-updater)، [توثيق electron-builder الموافق للإصدار المفحوص](https://github.com/electron-userland/electron-builder/blob/512a57ec9bcda593d3e0970bd2b9a33a63beeb57/website/docs/features/auto-update.md).

نسخ npm المستقرة التي تحققت منها الخطة هي `electron-builder 26.15.3` و`electron-updater 6.8.9`. هما مرشحان للتجربة، وليسا اعتمادين مثبتين أو متحققين داخل CubeCroom. ينبغي تثبيت النسخ التي تنجح في التجربة داخل القفل. بعض توثيق فرع master يتناول واجهات أحدث، فلا يُنسخ منه إعداد للإصدار 6.8.9 دون مراجعة مصدر نسخته. [سجل builder](https://registry.npmjs.org/electron-builder/26.15.3)، [سجل updater](https://registry.npmjs.org/electron-updater/6.8.9).

### حزم الإصدار ونطاق الدعم المقترح

| النظام | ملفات التوزيع المقترحة | التحقق المطلوب |
| --- | --- | --- |
| Windows x64 | NSIS `.exe` + metadata وblockmap التي يولدها builder | توقيع Authenticode موثوق، timestamp، تثبيت بحساب مستخدم عادي، وتحديث نسخة مثبتة |
| macOS Apple Silicon وIntel | DMG للتثبيت + ZIP للتحديث لكل معمارية | Developer ID، إعدادات Hardened Runtime الملائمة، notarization وstapling، واختبار عملي لكل معمارية |
| Linux x64 | AppImage + metadata | تشغيل على توزيعات محددة ومعلنة، تحقق من أصالة التحديث، واختبار صلاحية استبدال ملف AppImage وإعادة التشغيل |

هذه مصفوفة البداية المقترحة؛ الحد الأدنى لنسخة كل نظام والتوزيعات المدعومة يحددان بعد ترقية Electron وتجارب الحزم. لا تُعلَن معماريات إضافية، مثل Windows ARM64، قبل اختبارها. ZIP وحده ليس تعهداً بأنه يدعم OTA. [التوقيع والتوقيت على Windows](https://learn.microsoft.com/en-us/windows/win32/seccrypto/signtool)، [توزيع macOS الموثّق](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution).

### التوقيع وLinux

تُختبر صلاحية توقيع حزم Windows وmacOS وهوية الناشر المتوقعة قبل الإتاحة. التوقيع لا يُقدَّم كوعد بإزالة كل تحذيرات النظام.

في مسار AppImage المفحوص من 6.8.9، التنزيل والتحقق من المحتوى لا يقدمان تحققاً مماثلاً لهوية ناشر Windows/macOS. **checksum وحده ليس توقيعاً مستقلاً** إذا استطاع مهاجم تبديل الملف وmetadata معاً. [مصدر AppImageUpdater للنسخة المفحوصة](https://github.com/electron-userland/electron-builder/blob/electron-updater%406.8.9/packages/electron-updater/src/AppImageUpdater.ts).

التصميم المقترح لـLinux: توقيع بيان إصدار بمفتاح إصدار منفصل، وربط التوقيع بالإصدار والقناة والنظام والمعمارية وبصمة الملف. يحمل التطبيق المفتاح العام ويتحقق من البيان والملف قبل السماح بالتثبيت، بما في ذلك الملفات المحفوظة مؤقتاً وإعادة تشغيل التطبيق. لا يُرسل المفتاح الخاص إلى العميل. هذه إضافة خاصة بالمشروع تتطلب إثباتاً عملياً لمسار المنع والتثبيت وتدوير المفاتيح؛ ليست ميزة جاهزة نُسبت إلى المكتبة. إذا لم تنجح التجربة دون الاعتماد على واجهات داخلية هشة، يُعتمد مستودع حزم Linux موقّع وتحديثات مدير الحزم، ويُعدّل القرار قبل الإطلاق. لا يُعلن اكتمال OTA على Linux قبل حسم هذا الاختبار.

## 4. تنظيم التنفيذ داخل المشروع

| المكان المقترح | المسؤولية |
| --- | --- |
| إعداد إصدار مركزي في `scripts/release/` | هوية التطبيق `com.cubecroom.app`، المستودع الرسمي، القنوات، أسماء الملفات ومصفوفة الأهداف؛ يقرأه التغليف والتحقق وتوليد بيانات التنزيل |
| `package.json` في الجذر | مصدر رقم إصدار المنتج؛ Release PR يزامن نسخة desktop معه ويختبر التطابق؛ وقت التشغيل يقرأ `app.getVersion()` |
| `apps/desktop/src/updates/` | نسخة واحدة من خدمة التحديث في main process: الفحص والتنزيل والتحقق والتثبيت والإخفاقات |
| `packages/contracts` | حالات وأوامر ونتائج التحديث عبر IPC والتحقق منها؛ دون اعتماد مشترك على Electron |
| دورة حياة desktop + `packages/core` | انتظار الحفظ وعمليات AI/الملفات، منع كتابات جديدة مؤقتاً، إعادة استخدام النسخ الاحتياطي، وإغلاق الخادم وقاعدة البيانات بأمان |
| teacher-ui و`packages/ui` | عرض الحالة والإصدار وملاحظات الإصدار وخياري التنزيل/إعادة التشغيل باستخدام المكونات المشتركة وTailwind |
| docs landing page | عرض روابط النسخة المنشورة وملفاتها من بيان نشر واحد، لا كتابة أرقام وروابط مكررة يدوياً |

لا تُنشأ حزمة عامة جديدة لمجرد وجود وحدة صغيرة. يُفصل محوّل Electron عن السياسة القابلة للاختبار، وتُعاد الاستفادة من عقود IPC والتخزين والنسخ الموجودة. لا يُسمح للـrenderer أو بوابة الطالب بإرسال مسار مثبت أو URL تحديث عشوائي.

عند تغيير Forge إلى builder، تُنقل صراحة موارد teacher-ui الثابتة وstudent-web standalone وترحيلات DB، ويُضبط ASAR/unpack للثنائيات الأصلية. يجب أن يفحص التحقق **محتوى الحزمة والمثبت الناتج**، لا مجلد البناء فقط. لا تُعطّل `ELECTRON_RUN_AS_NODE` كتقوية عامة قبل استبدال اعتماد خادم الطلاب عليه بطريقة متحققة.

## 5. تجربة التحديث وحماية الحصة والبيانات

1. فحص خفيف بعد جاهزية التطبيق، ثم فحوص متباعدة قابلة للضبط مع backoff عند الانقطاع، وزر فحص يدوي. قناتان واضحتان: stable افتراضياً وbeta باختيار المستخدم.
2. عرض النسخة وملاحظات الإصدار وحجم التنزيل. التوصية الأولية: تنزيل باختيار المعلم، مع خيار تنزيل تلقائي لاحقاً. يستمر البرنامج محلياً إذا تعذر الوصول إلى GitHub.
3. تنزيل واحد متزامن كحد أقصى، مع تقدم ملخّص للواجهة، والتحقق من البصمة والتوقيع والمسار والنسخة والمعمارية. يوضع الملف في cache خارج بيانات المعلم.
4. يصبح التحديث جاهزاً، لكن يُمنع التثبيت أثناء حصة نشطة أو وجود حفظ غير مكتمل. يظهر خيار «إعادة التشغيل والتحديث» عندما يصبح آمناً.
5. قبل التثبيت: انتظار تأكيد حفظ المحرر، تسوية عمليات AI والملفات الجارية، منع كتابات جديدة، إيقاف استقبال عمل جديد من بوابة الطلاب، وإنشاء نسخة احتياطية متسقة للقاعدة والمرفقات. فشل الحفظ أو النسخ أو نقص المساحة يمنع التثبيت ويعيد التطبيق إلى حالة قابلة للاستخدام.
6. إغلاق خادم الطلاب وقاعدة البيانات، ثم استدعاء المثبت. تُنسَّق هذه الخطوات قبل `quitAndInstall`؛ معالج `before-quit` الحالي وحده لا يكفي للانتظار غير المتزامن.
7. عند التشغيل الجديد: فحص سلامة البيانات، تنفيذ الترحيلات المطلوبة، والتحقق من فتح قاعدة البيانات والواجهة وإمكان تشغيل البوابة. تعرض نتيجة مفهومة ومسار الاسترداد إذا فشل الإقلاع.

في مصدر updater 6.8.9، `autoInstallOnAppQuit` مفعّل افتراضياً؛ تقترح الخطة تعطيله حتى يمر التثبيت عبر بوابة الحفظ. ويُضبط `allowDowngrade=false` صراحة بعد تغيير القناة، لأن setter القناة يفعّله. هذه الإعدادات وحدها لا تغني عن اختبار دورة الحياة على الأنظمة الثلاثة. [مصدر AppUpdater](https://github.com/electron-userland/electron-builder/blob/electron-updater%406.8.9/packages/electron-updater/src/AppUpdater.ts).

**سياسة الاسترداد:** إصدار إصلاح برقم أعلى هو المسار الافتراضي بعد إصدار معيب. لا يُفتح DB حديث ببرنامج قديم. الاسترداد من نسخة احتياطية عملية صريحة، تحفظ البيانات الحالية أولاً وتوضح احتمال فقد التعديلات اللاحقة للنسخة. لا يُوعَد بتراجع تلقائي أو بتثبيت مقاوم لانقطاع الكهرباء قبل إثباته عملياً.

**الانتقال الأول:** لأن التطبيق الحالي بلا محدث، يحتاج المستخدم إلى تنزيل المثبت الجديد مرة واحدة. تُختبر ترقية/إزالة Squirrel مع الحفاظ على مجلد البيانات المخصص والمفاتيح المحلية والاختصارات وهوية التطبيق. إبقاء اسم التطبيق وحده لا يثبت أن NSIS سيزيل Squirrel تلقائياً. لا يُمسح مجلد بيانات المستخدم أثناء التثبيت أو إزالة البرنامج القديم.

**السجلات:** أحداث محلية منظمة تشمل رقم الإصدار والمرحلة والنظام والمعمارية ورمز الخطأ والمدة، مع تدوير وحجم محدود وتصدير تشخيص اختياري. تُستبعد مفاتيح المزودات ورموز الجلسات ومحتوى الطلاب. لا تُفترض مراقبة مركزية أو رفع تلقائي للسجلات؛ نجاح نسبة نشر تجريبية لا يُستنتج من غياب بيانات لم تُجمع أصلاً.

## 6. أتمتة الإصدارات والنشر

المسار المقترح: **مساهمة → فحوص PR → دمج → Release PR → دمج Release PR → بناء وتوقيع واختبار → نشر الإصدار المكتمل → تحديث بيانات صفحة التنزيل.** دمج Release PR هو قرار إطلاق النسخة؛ بقية المسار آلي إذا نجحت البوابات.

1. **تثبيت الأساس:** إصلاح تعارض pnpm بإبقاء النسخة في `packageManager` فقط، واستخدام ملف Node المركزي والقفل. اختيار إصدارات runners صراحة ومراجعة ترقياتها بدلاً من ترك دعم المنتج تابعاً لمعنى `*-latest` المتغير.
2. **Release Please:** توليد رقم الإصدار وCHANGELOG وRelease PR من Conventional Commits، بمكوّن إصدار واحد يمثل المنتج كله، بما فيه تغييرات الحزم المشتركة. تبقى نسخة مخطط DB مستقلة. تُزامن نسخة desktop ضمن PR نفسه، ويمنع CI أي اختلاف.
3. **Draft أولاً:** إنشاء draft release مربوط بcommit محدد. تُختبر إعدادات draft وإنشاء tag في نسخة Release Please المثبتة؛ الوثائق تشرح أن draft لا ينشئ tag فوراً افتراضياً وتوفر خياراً لذلك. تعتمد وظائف البناء اللاحقة على SHA/مخرجات وظيفة الإصدار في المسار نفسه، لا على تحرك main لاحقاً. [إعدادات manifest](https://github.com/googleapis/release-please/blob/main/docs/manifest-releaser.md).
4. **تشغيل workflows فعلياً:** يوصى بـGitHub App مخصص بأقل صلاحيات لازمة لإنشاء PR الإصدار كي تعمل فحوصه. أحداث PR/tag/release الناتجة عن `GITHUB_TOKEN` لا تشغّل عادة workflows جديدة؛ لا تُبنى الخطة على انتظار حدث لن يصل. تُربط أعمال التغليف بعد وظيفة الإصدار مباشرة أو باستدعاء صريح موثّق. [سلوك Release Please والتوكن](https://github.com/googleapis/release-please-action).
5. **البناء والتحقق:** تثبيت بالقفل، typecheck/lint/tests/build/smoke، ثم بناء حزم فعلية على أنظمتها ومعمارياتها. فصل cache بحسب النظام والمعمارية وإصدارات Node/Electron والقفل، خصوصاً better-sqlite3. لا يُورّث منع تنزيل Electron إلى وظائف تشغيله.
6. **التوقيع:** يتم في وظائف موثوقة، مع أسرار التوقيع فقط حيث تلزم، ثم فحص التوقيع والموارد ورقم الإصدار وإجراء اختبارات الحزمة. يُنتج جرد تراخيص ومكونات مشحونة وبيان ملفات وبصمات. سجلات الفشل ترفق كأدلة دون أسرار.
7. **التجميع والنشر مرة واحدة:** تعمل أدوات التغليف بـ`--publish never`. تجمع وظيفة واحدة كل مخرجات الأنظمة والتواقيع وmetadata؛ تتحقق من عدم تصادم أسماء ملفات المعماريات واكتمال الروابط، ثم ترفعها إلى draft وتنشره بعد نجاح الجميع. عند فشل نظام يبقى الإصدار مسودة. النشر ليس ادعاءً بعملية ذرية عبر GitHub ومضيف docs.
8. **التعافي من فشل الأتمتة:** إعادة المحاولة تحدد الإصدار وSHA الموجودين وتستأنف المسودة؛ لا تعتمد فقط على إشارة «أُنشئ الآن». قفل نشر لكل قناة/إصدار يمنع التنافس والنشر المزدوج، ولا تُلغى وظيفة في منتصف النشر. لا تستبدل ملفات إصدار منشور بصمت؛ الإصلاح إصدار جديد.
9. **صفحة التنزيل:** توليد بياناتها من الإصدار المنشور فقط، والتحقق من التنزيل دون تسجيل دخول. فشل نشر docs يحتفظ بآخر بيانات سليمة ويسمح بإعادة المحاولة؛ لا يُسقط التطبيق. استضافة docs الحالية خارج الخطة المثبتة وتحتاج تحديداً قبل كتابة تكامل نشرها.

تثبّت Actions على commit SHA مراجع، وتمنح `contents: read` افتراضياً، مع صلاحيات كتابة محدودة لوظائف الإصدار. لا تصل أسرار التوقيع إلى PRs من forks ولا يُشغّل كودها بصلاحيات `pull_request_target`. تُحمى ملفات workflows والترخيص والتحديث بواسطة CODEOWNERS وفحوص دمج مطلوبة. تُفصل مفاتيح توقيع الإصدار عن صلاحية تعديل مستودع التوزيع بقدر ما تسمح البنية المختارة. [إرشادات GitHub الأمنية](https://docs.github.com/en/actions/reference/security/secure-use).

تبدأ القنوات بـbeta وstable دون خدمة rollout مخصصة. ترقية `x.y.z-beta.n` إلى `x.y.z` تحتاج حزمة تحمل الرقم النهائي؛ تغيير اسم ملف beta لا يحوّله إلى إصدار stable. تبقى حزم الإصدارات السابقة وبيانات النسخ الاحتياطية متاحة وفق سياسة احتفاظ محددة، لتوفير الاسترداد والتحقيق.

- **النشر:** فشل منصة واحدة، تأخر notarization، إعادة تشغيل workflow بعد إنشاء draft، تصادم أسماء معماريات، فشل نشر docs، وتنزيل دون حساب؛ تبقى آخر نسخة سليمة قابلة للتنزيل.

## 10. ما لم يُحسم وما لم يُختبر

حسم المالك الاسم القانوني وUAE ومجانية إعادة البيع وwhite-label والاستضافة التعليمية. المطلوب قبل اعتماد الرخصة الآن هو مراجعة النص المرشح وسلسلة الحقوق والتبعيات، واعتماد طريقة تسجيل قبول المساهمين وحماية سجلاتها، ثم إقرار النسخة المحددة من الوثائق. والمطلوب قبل الإصدار: توفر شهادات Windows وحساب Developer ID، جرد النسخ التي وُزعت يدوياً، تحديد استضافة docs، وتأكيد المنصات/المعماريات الدنيا بعد التجربة. تكاليف التوقيع والبناء والاستضافة غير مقدرة هنا لعدم توفر هذه المدخلات.

**لم تُبنَ أو تُوقَّع أو تُنشر حزمة OTA ضمن إعداد هذه الخطة، ولم تُجرَ تجربة A→B على Windows أو macOS أو Linux.** نتائج تشغيل التطوير المحلي السابقة لا تثبت صلاحية التحديث، وآخر CI بعيد مفحوص فاشل قبل الاختبارات. تنفيذ هذه الخطة يبدأ بإصلاح ذلك الأساس ثم جمع أدلة القبول المذكورة.
