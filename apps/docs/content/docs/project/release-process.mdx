يجمع Release Please التغييرات المدمجة في الفرع الرئيسي ويُحدّث طلب دمج واحداً للإصدار القادم. يحتوي الطلب على رقم النسخة في التطبيق وسجل التغييرات، وتعمل عليه فحوص Windows وLinux وmacOS بمعماريتي Intel وApple Silicon.

## من التغيير إلى الإصدار

1. ادمج التحسينات بعناوين Conventional Commits، مثل fix: لإصلاح عيب وfeat: لميزة جديدة.
2. راجع [طلب الإصدار على GitHub](https://github.com/cubetek/cubeCroom/pulls)، ورقم النسخة وسجل التغييرات ونتائج الفحوصات.
3. عند دمج طلب الإصدار، تبدأ عملية البناء تلقائياً من نسخة الشيفرة المحددة في ذلك الدمج.
4. تُختبر الحزم وتُجمع نتائج الأنظمة الأربعة قبل نشر الملفات في [GitHub Releases](https://github.com/cubetek/cubeCroom/releases).
5. تقرأ [صفحة التنزيل](/download) و[سجل التغييرات](/changelog) النسخة المنشورة وتاريخها وروابطها تلقائياً.

## وضع النشر الحالي

سياسة النشر الحالية هي Preview: تُنشر الحزم كإصدار تجريبي مع بصمات SHA-512 وإثبات منشأ البناء من GitHub. لا تتطلب هذه العملية إعداد GitHub App أو مفاتيح وصول شخصية. يظل تحديث النسخ التجريبية يدوياً، ولا يعني نجاح البناء تفعيل OTA أو توفر توقيع النظام.

وضع النشر الموقّع مسار مستقل في إعداد المشروع. يتطلب شهادات المنصات ومفتاح توقيع بيانات التحديث؛ فشل التوقيع لا يحوّل النسخة تلقائياً إلى إصدار تجريبي. راجع [جاهزية OTA](/docs/releases/updates#جاهزية-ota).

## إذا فشل البناء

تبقى النسخة مسودة لا تظهر ضمن التنزيلات العامة. راجع الخطأ في [GitHub Actions](https://github.com/cubetek/cubeCroom/actions)، ثم أعد تشغيل العمل الفاشل أو استأنف المسودة باستخدام اسم الوسم ومعرّف الشيفرة الكامل وفق [دليل عمليات الإصدار](https://github.com/cubetek/cubeCroom/blob/main/scripts/release/README.md). لا تُستبدل ملفات إصدار منشور بملفات مختلفة تحمل رقم النسخة نفسه.
